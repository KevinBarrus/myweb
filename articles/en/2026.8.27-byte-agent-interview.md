## 2026.8.27 ByteDance Agent Development Interview — A Hands-on Analysis

### Problem

```text
Merge nested JSON

Question description

Given two JSON data structures with arbitrary nesting, implement a merge function. The rules are:

Dictionary (dict): recursively merge values under the same key; keep keys that appear in only one dictionary

List (list): concatenate (json1 list + json2 list)

Integer / floating-point number (int/float): add (json1 value + json2 value)

String (str): concatenate (json1 string + json2 string)

Boolean (bool): logical OR (the result is True if either value is True)

Other types, such as None: let json2 overwrite json1.

Requirement: return a new merged JSON value without modifying the original data.

Example 1 (merging multiple types, including lists):

Input:

json1 = {"a": 1, "b": [1,2,3], "c": False, "d": 2.5}
json2 = {"a": 2, "b": [3,4,5], "c": True, "d": 3.5}

Output:

{"a": 3, "b": [1,2,3,4,5], "c": True, "d": 6.0}

Example 2 (multiple nesting levels + lists):

Input:

json1 = {"x": {"y": {"z": [10,20], "m": [1]}}}
json2 = {"x": {"y": {"z": [20,30], "m": [2], "n": None}}}

Output:

{"x": {"y": {"z": [10,20,30], "m": [1,2], "n": None}}}
```

Note: the interview question calls the inputs “JSON”, but the original examples use `False`, `True`, and `None`. These are Python literals, not the `false`, `true`, and `null` used in strict JSON text. Below, `json1` and `json2` are treated as already-parsed Python nested objects, and `ast.literal_eval` is used to reproduce the input format shown in the prompt. If the input is strict JSON text, use `json.loads` instead.

Note: the stated list rule is “concatenate”, but the examples show that duplicate elements should be removed. This article follows the examples and implements stable concatenation with deduplication: the first occurrence is kept and the original order is preserved.

### 1. Overall approach

JSON has a recursive structure: a `dict` value may itself be another `dict` or a `list`. Therefore, when both inputs contain a value under the same `key`, the final result cannot be decided at the current level alone. The same merge rules must be applied to the two values again. It is therefore natural to define `merge_json(a, b)` as a recursive function.

The six cases and their rules are:

| Condition | Result |
| --- | --- |
| `a` and `b` are both `dict` | Recursively merge |
| `a` and `b` are both `list` | Concatenate, then perform stable deduplication |
| `a` and `b` are both `bool` | `a or b` |
| `a` and `b` are both `int` / `float` | `a + b` |
| `a` and `b` are both `str` | `a + b` |
| Other cases | Let `b` overwrite `a` |

### 2. Important edge cases

#### 2.1 Check `bool` before `int` / `float`

In Python, `bool` is a subclass of `int`. Consequently, both `isinstance(True, int)` and `isinstance(False, int)` return `True`. If the numeric branch only uses `isinstance(x, (int, float))`, boolean values will also satisfy it. Therefore, `bool` must be handled first, or the numeric branch must explicitly exclude `bool`.

#### 2.2 Do not modify the original JSON (the shallow/deep copy issue)

Returning a new JSON value means more than creating a new outer `dict`: nested `list` and `dict` objects must not share identity with the original data either. For example:

```python
json1 = {
    "a": {
        "b": [1, 2, 3]
    }
}
```

If you write:

```python
res = {}
res["a"] = json1["a"]
```

`res` looks like a new dictionary, but `res["a"] is json1["a"]` is actually `True`. In other words, the value of `"a"` points to the same `dict` object in both structures. If you then run `res["a"]["b"].append(4)`, `json1` becomes:

```python
{
    "a": {
        "b": [1, 2, 3, 4]
    }
}
```

That violates the requirement to return a new merged JSON value without modifying the original data. Assigning `res["a"] = json1["a"]` only creates another reference; it does not copy the nested data. A shallow copy cannot solve this nested case either:

```python
res = json1.copy()
```

or:

```python
res = dict(json1)
```

The outer containers are different, so `res is json1` is `False`, but `res["a"] is json1["a"]` is still `True`. Therefore, `res["a"]["b"].append(4)` still modifies `json1`.

This is what a shallow copy means: it copies only the first-level container, while nested objects are still shared. `deepcopy` recursively processes nested objects:

```python
import copy

res = copy.deepcopy(json1)
```

Now:

- `res is json1` is `False`;
- `res["a"] is json1["a"]` is also `False`;
- `res["a"]["b"] is json1["a"]["b"]` is also `False`.

`deepcopy` recursively processes nested objects and creates independent copies of mutable objects where necessary. The nested mutable objects in the result therefore no longer share identity with the input.

After `res["a"]["b"].append(4)`:

```python
print(res)
# {'a': {'b': [1, 2, 3, 4]}}

print(json1)
# {'a': {'b': [1, 2, 3]}}
```

The original data is unaffected.

Returning to this JSON merge problem, the following case is especially easy to get wrong:

```python
json1 = {
    "a": 1
}

json2 = {
    "a": 2,
    "config": {
        "items": [1, 2]
    }
}
```

If you write:

```python
res["config"] = json2["config"]
```

the result looks correct:

```python
res = {
    "a": 3,
    "config": {
        "items": [1, 2]
    }
}
```

But in fact:

```python
res["config"] is json2["config"]
# True
```

Then:

```python
res["config"]["items"].append(3)
```

also modifies `json2`.

The correct form is:

```python
res["config"] = copy.deepcopy(json2["config"])
```

Why do `int`, `str`, and `bool` usually not require this concern? They are immutable objects. For example:

```python
a = 10
b = a
```

`b = 20` does not change `a` to 20. Strings behave similarly:

```python
a = "hello"
b = a

b += " world"
```

The result is:

```python
a
# "hello"

b
# "hello world"
```

Python creates a new string for `b` rather than modifying the original string. The objects that require real caution are `dict`, `list`, `set`, and other mutable objects. The complex structures in JSON are primarily `dict` and `list`.

So, in an interview, explain this pitfall clearly: the problem requires the original JSON not to be modified, so nested `dict` and `list` objects in the result must not share references with the inputs. Ordinary assignment and shallow copies only copy references. For a composite value that is being kept or overwritten directly, use `deepcopy` to prevent nested mutable objects in the result from sharing references with the input.

### 3. Understanding the model through C/C++ objects and pointers

#### 3.1 Use C++ pointers as a mental model

For example:

```python
a = [1, 2, 3]
b = a
```

Do not think of this as `a` storing `[1,2,3]` and `b` copying another `[1,2,3]`. It is closer to:

```text
a --> [1, 2, 3]  (Python heap object)
b --> [1, 2, 3]  (same object)
```

Therefore, `a is b` is `True`. Using C++ as an approximate mental model:

```cpp
vector<int>* a = new vector<int>{1, 2, 3};
vector<int>* b = a;
```

CPython's implementation is of course more complicated, but this mental model is useful for understanding references.

#### 3.2 `list` and `dict` store references to other Python objects

This is the key to understanding shallow copies. For example:

```python
a = [
    [1, 2],
    [3, 4]
]
```

You may instinctively picture:

```text
a --> [[1, 2], [3, 4]]
```

The more accurate model is:

```text
a --> outer list
outer list[0] --> [1, 2]
outer list[1] --> [3, 4]
```

The outer `list` stores references to the inner Python objects. It can be roughly compared with this C++ structure:

```cpp
vector<vector<int>*> a;
```

This is only a mental model; a Python `list` is not actually this C++ type.

#### 3.3 Shallow copy: create a new container and copy its references

Now:

```python
import copy

a = [
    [1, 2],
    [3, 4]
]

b = copy.copy(a)
```

The operation can be understood in two steps.

**Step 1: create a new outer list**

```text
a --> List A
b --> List B
```

Thus, `a is b` is `False`.

**Step 2: copy the references stored in A into B**

The final structure is:

```text
a --> List A
b --> List B
List A[0] --> [1, 2] <-- List B[0]
List A[1] --> [3, 4] <-- List B[1]
```

Therefore, `a is b` is `False`, but `a[0] is b[0]` is `True`. This is why a shallow copy copies only the first level.

More precisely, it is not that shallow copying is defined to “copy only one level”. It creates a new outermost container, then copies the element references as-is without recursively copying the referenced objects.

#### 3.4 Why does modifying `b[0]` affect `a`?

Now:

```python
b[0].append(100)
```

This does not modify `b` itself. It follows `b[0]` to the inner `list` and modifies that list in place. Since `a[0]` and `b[0]` point to the same object, the result of `print(a)` is:

```python
[
    [1, 2, 100],
    [3, 4]
]
```

What actually happened was:

```text
a[0] --> [1, 2] <-- b[0]
                 append(100)
```

#### 3.5 Why does this operation not affect `a`?

`a` does not change here because the original `[1, 2]` is not modified; only the reference stored at index 0 of `b` is replaced. The original structure is:

```text
a[0] --> [1, 2] <-- b[0]
```

After `b[0] = [100, 200]`, `a[0]` points to `[1, 2]` and `b[0]` points to `[100, 200]`. They no longer point to the same object. Therefore:

```python
print(a)
# [[1, 2], [3, 4]]

print(b)
# [[100, 200], [3, 4]]
```

This distinction is important: `b[0].append(100)` obtains the inner `list` through `b[0]` and mutates that object in place; `b[0] = [100]` changes the object reference stored by the outer container `b` at index 0.

#### 3.6 The recursive copying mechanism of `deepcopy`

Now:

```python
b = copy.deepcopy(a)
```

`deepcopy` does not stop after creating a new outer `List B`; it continues recursively. When it finds:

```text
a --> list --> nested list
```

it copies the inner `list` as well. The final structure is:

```text
a --> List A --> List X  [1, 2]
             --> List Y  [3, 4]

b --> List B --> List X' [1, 2]
             --> List Y' [3, 4]
```

Thus:

- `a is b` is `False`;
- `a[0] is b[0]` is `False`;
- `a[1] is b[1]` is `False`.

Consequently, `b[0].append(100)` modifies `List X'`, while `a[0]` points to `List X`; they are completely different objects.

#### 3.7 Comparing Python copies with C++ object models

Suppose we design the following structure ourselves:

```cpp
struct Node {
    vector<int>* data;
};
```

Then:

```cpp
Node a;
a.data = new vector<int>{1, 2, 3};
```

A shallow copy is similar to `Node b = a`, resulting in:

```text
a.data --> vector{1, 2, 3} <-- b.data
```

That is, `a.data == b.data`.

A deep copy is more like:

```cpp
Node b;
b.data = new vector<int>(*a.data);
```

The result is:

```text
a.data --> vector A {1, 2, 3}
b.data --> vector B {1, 2, 3}
```

This is a useful way to understand the essential difference between Python's `copy.copy(a)` and `copy.deepcopy(a)`.

#### 3.8 `deepcopy` is not a raw memory copy

Suppose:

```python
a = {
    "x": [
        {"name": "Kevin"}
    ]
}
```

The object relationships are actually:

```text
dict --> list --> dict --> str
```

`deepcopy(a)` is not simply a matter of allocating one contiguous block of memory and calling `memcpy(...)`. It is closer to:

```text
copy outer dict
  --> find a list value
  --> copy list
  --> find a dict element
  --> copy dict
  --> continue recursively
```

In other words, `deepcopy` recursively copies an object graph rather than copying one contiguous memory region. Python also does not guarantee that a `dict`, `list`, and nested `dict` are stored contiguously in one block of memory.

#### 3.9 How `deepcopy` handles immutable objects

For example:

```python
import copy

a = "hello"
b = copy.deepcopy(a)

print(a is b)
```

You might expect the result to always be `False`, but it can in fact be `True`. Since strings are immutable, there is no need to create another copy. Similarly, immutable objects such as `int`, `float`, `str`, `bool`, and `None` can be shared safely.

`deepcopy` mainly needs to create independent copies for `list`, `dict`, `set`, and custom mutable objects.

#### 3.10 Returning to the JSON merge problem

For example:

```python
json1 = {
    "config": {
        "ports": [8000, 8080]
    }
}
```

If you write `res = json1.copy()`, the structure is effectively:

```text
json1 --> outer dict A --> config dict --> ports list
res   --> outer dict B --> config dict --> ports list
```

Only outer `dict A` and outer `dict B` are different objects. The inner `config dict` and `ports list` are still shared.

By contrast, `res = copy.deepcopy(json1)` produces something like:

```text
json1 --> dict A --> config A --> ports A
res   --> dict B --> config B --> ports B
```

The two object graphs are genuinely separated.

The most important Python mental model to keep is this: when you see `a = xxx`, do not imagine “put the value `xxx` into variable `a`”. It is closer to “make the name `a` refer to a Python object”.

Therefore, `b = a` adds another reference to the same object. `b = copy.copy(a)` creates a new outermost object, but copies the references stored inside it. `b = copy.deepcopy(a)` recursively copies the mutable object graph, decoupling nested mutable objects from the original wherever necessary.

### 4. Solution code

```python
import copy
import ast

def merge_json(a, b):
    # 1. dict: recursively merge
    if isinstance(a, dict) and isinstance(b, dict):
        res = {}

        # Process json1 first
        for key, value in a.items():
            if key in b:
                # The key exists in both objects, so merge the values recursively.
                # A value may have any supported type, which is why recursion is needed.
                res[key] = merge_json(value, b[key])
            else:
                # The key exists only in json1, so make a deep copy.
                res[key] = copy.deepcopy(value)

        # The remaining keys exist only in json2.
        for key, value in b.items():
            if key not in a:
                # The same deep-copy rule applies here.
                res[key] = copy.deepcopy(value)

        return res

    # 2. list: concatenate + deduplicate
    if isinstance(a, list) and isinstance(b, list):
        res = []

        for x in a + b:
            # Deduplicate while preserving the first occurrence.
            if x not in res:
                # A list element may itself be a list or dict, so copy it deeply.
                res.append(copy.deepcopy(x))
        return res

    # 3. bool must be checked before int/float because bool is a subclass of int.
    if isinstance(a, bool) and isinstance(b, bool):
        return a or b

    # 4. int/float; explicitly exclude the case where either value is bool.
    if (
        isinstance(a, (int, float))
        and not isinstance(a, bool)
        and isinstance(b, (int, float))
        and not isinstance(b, bool)
    ):
        return a + b

    # 5. str
    if isinstance(a, str) and isinstance(b, str):
        return a + b

    # 6. Other cases: json2 overwrites json1.
    # For example, if a is None and b is a list or dict, deep-copy b.
    # Type mismatches also reach this branch.
    return copy.deepcopy(b)

def solve():
    # Local test entry point: the two lines in case1.txt are "json1 = ..." and "json2 = ...".
    # The interview question only requires merge_json and does not define a file format.
    with open("case1.txt", "r", encoding="utf-8") as f:
        line1 = f.readline().strip()
        line2 = f.readline().strip()

    json1 = ast.literal_eval(line1.split("=", 1)[1].strip())
    json2 = ast.literal_eval(line2.split("=", 1)[1].strip())

    ans = merge_json(json1, json2)

    print(ans)


if __name__ == "__main__":
    solve()
```

### 5. Complexity analysis

Assume the total size of the two JSON values is $N$ and the maximum nesting depth is $D$. Here, $N$ denotes the total number of nodes in the entire nested JSON structure.

For a `dict`, key lookup takes average $O(1)$ time. If a `list` is only concatenated, recursive merging needs to traverse the input JSON, so the overall time complexity is $O(N)$.

The current implementation also performs stable deduplication on lists. For a list of length $k$, `x not in res` may linearly scan the result accumulated so far. If equality comparison for an individual element is temporarily treated as $O(1)$, deduplicating that list takes $O(k^2)$ time in the worst case.

In reality, elements in a JSON list may themselves be nested `list` or `dict` values, so equality comparison can recursively inspect their internal structures. Thus, $O(k^2)$ describes only the number of outer membership comparisons, not the full comparison cost for arbitrary nested JSON. Measured against the total input size $N$, a rough worst-case upper bound for the current implementation is $O(N^2)$.

Because the problem requires the original JSON not to be modified, a new result must be constructed. The result itself requires $O(N)$ space, while the recursive call stack requires at most $O(D)$ space. Therefore, total auxiliary space can be written as $O(N+D)$. If output space is counted separately, the extra space used by the recursion stack is $O(D)$.

### 6. Possible optimizations

If the interviewer asks for a further optimization, a hash-based structure can be considered for list deduplication. The current `x not in res` check scans `res` linearly, so one membership test costs $O(k)$ and list deduplication takes $O(k^2)$ in the worst case. If equality comparison for an individual element is temporarily treated as $O(1)$, deduplicating a list of length $k$ through linear membership checks has worst-case complexity $O(k^2)$. For nested `list` or `dict` elements, equality comparison may add further cost.

An additional `seen` hash set could reduce membership checks to average $O(1)$. However, elements in a JSON list may still be `list` or `dict` values, which are unhashable in Python. Therefore, `seen.add(x)` cannot be used directly.

One option is to recursively convert each JSON element into a canonical, hashable representation. For example, convert a `list` into a `tuple` containing the normalized representation of each element, and convert a `dict` into a `tuple` of `(key, value)` pairs sorted by key. That representation can then be inserted into `seen`.

Note that constructing a canonical representation also requires traversing the nested JSON. Normalizing a `dict` may additionally require sorting. Therefore, this optimization improves the membership-checking process, but it is not correct to claim that the entire algorithm simply changes from $O(k^2)$ to $O(k)$.

**Terminology:**

- **hashable representation:** a form that converts a JSON object that cannot be placed in a `set` or used as a `dict` key into an equivalent hashable value.
- **canonical representation:** a stricter form that maps equal JSON contents to exactly the same standard representation, regardless of their original representation order.
